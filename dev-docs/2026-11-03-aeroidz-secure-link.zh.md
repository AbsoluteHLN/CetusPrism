# AeroidzServer / AeroidzCilent 安全链路方案探索（2026-11-03）

分支已建：`AeroidzServer`（服务端）、`AeroidzCilent`（本地特供客户端；按你的拼写保留）。目标：**服务端托管 + 本地特供能力，最终实现安全链路的远程连接**。本文件是方案对比与建议，不是实现。

## 威胁模型（先定边界）

- 服务端持有：会话日志、模型凭据（或凭据代理）、文件系统访问
- 链路穿越：不可信网络（公网/公司网），可能经过代理
- 对手：被动窃听、主动中间人、重放、客户端仿冒、服务端仿冒
- **本地特供**意味着客户端在操作者自己的机器上，可持有私钥/设备密钥，不需要第三方 PKI 也能建立信任

## 候选方案对比

| 方案 | 信任基础 | 优点 | 代价 | 适配度 |
|---|---|---|---|---|
| **A. WireGuard 底层 + 应用层 TLS** | 设备密钥对 | 内核级性能、漫游好、密钥简单 | 需系统级安装/授权；NAT 穿透要协调 | ★★★★（本地特供最自然） |
| **B. mTLS（双向 TLS）+ 短时效证书** | 双方证书，自签 CA 或 pinning | 应用层自足、HTTP/2 复用、标准库支持 | 证书分发/轮换要做成产品功能 | ★★★★☆ |
| **C. SSH 隧道（反向隧道）** | SSH 密钥 | 现成工具链、端口转发内置、用户熟悉 | 每会话一条 TCP、Windows 服务端配置繁琐 | ★★★（最快落地原型） |
| **D. Noise 协议框架（如 libp2p/noise）** | 握手模式（XX/XK） | 前向保密内建、消息轻量 | 需引入协议库、自研心跳/重连 | ★★★（适合后续自研协议） |
| E. 应用层 E2EE（会话事件加密） | 应用密钥对 | 端到端语义最强 | 与现有 typert/Remote 投影架构冲突大，检索/共享难以在密文上做 | ★★（不建议 v1） |

## 建议路线：B 打底，A 进化

**阶段 1（B，mTLS）**：在现有 `dsh-api`（远程 BFF）前面加双向 TLS。
- 服务端：自签根 CA（首次启动生成，展示指纹供客户端核对——TOFU 变体）
- 客户端：设备密钥对 + 证书签名请求（CSR）流程，服务端审批后签发短时效客户端证书（7 天，可吊销）
- 复用现有 HTTP/2 + typert Remote 投影，**应用层零改动**
- 凭据面：DEEPSEEK_API_KEY 留在服务端，客户端只拿会话能力——这正是"本地特供"的安全边界

**阶段 2（A，WireGuard 叠加）**：对高频/大流量场景（文件同步、快照传输）在 mTLS 之下再叠 WireGuard，应用无感。

**阶段 3（D，Noise）**：若未来要 P2P（liveshare 观看面），用 Noise IK 模式做会话级加密，与上游 liveshare 方向汇合。

## 必须内建的安全细节（无论选哪个）

1. **短时效 + 吊销**：证书/令牌 ≤7 天；服务端维护吊销清单（CRL 或内存 denylist）
2. **双向认证**：只认证服务端 =  half-done；客户端证书绑定设备密钥（Windows CNG / DPAPI 或 macOS Keychain）
3. **防重放**：握手内建 nonce（TLS/Noise 都有）；应用层操作带单调序号（会话日志 seq 天然单调，可直接用作防重放窗口）
4. **审计**：每次连接记录证书指纹、设备名、时间——复用现有 `docs/subsystems` 审计模式
5. **fail closed**：证书校验失败即断开，无降级到明文的路径

## 与上游的关系

上游本轮（dsh-v0.2.2-alpha.2）的 **liveshare** 面（~150 文件）实现了宿主/观看/客户端共享，但其安全模型假定同一信任域。我们的 mTLS 链路可以作为 liveshare 的传输底座，冲突点会在认证协商——backport liveshare 前先定传输契约。
